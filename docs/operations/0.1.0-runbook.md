# Wander 0.1.0 Operator Runbook

This runbook covers installation, configuration, migration, upgrade, rollback,
backup, restore, known limitations, and first-line troubleshooting for the
Wander 0.1.x release line.

## Supported starting points

- A new Wander cluster may be installed from a Wander release archive.
- An existing open-source HashiCorp Nomad 1.6.5 cluster may be migrated by
  replacing binaries in a rolling operation.
- Newer Nomad versions, Nomad Enterprise-only features, and downgrades from
  later state formats are not supported migration sources.
- Preview releases are for compatibility and UI testing. Use a stable 0.1.x
  release for production once one is published.

Always take a verified snapshot and retain the previous binary before changing
a cluster.

## Install a release archive

Release assets are published at
<https://github.com/open-wander/wander/releases>. Select the archive matching
the target operating system and architecture:

```text
wander_VERSION_linux_amd64.zip
wander_VERSION_linux_arm.zip
wander_VERSION_linux_arm64.zip
wander_VERSION_darwin_amd64.zip
wander_VERSION_darwin_arm64.zip
wander_VERSION_windows_amd64.zip
```

Download the archive and `wander_VERSION_SHA256SUMS` from the same release.
Verify the archive before extracting it. On Linux:

```shell
grep "wander_VERSION_OS_ARCH.zip" wander_VERSION_SHA256SUMS | sha256sum -c -
```

On macOS:

```shell
grep "wander_VERSION_OS_ARCH.zip" wander_VERSION_SHA256SUMS | shasum -a 256 -c -
```

Extract the archive, place `wander` (or `wander.exe`) on the service account's
`PATH`, and verify it:

```shell
wander version
wander -help
```

Release archives contain one executable with the web UI embedded. No Node.js
runtime or separate web server is required.

## Configure and start Wander

Wander retains the Nomad 1.6.5 HCL configuration, job-file, API, plugin, and
state contracts. Existing `.nomad` job files and inherited `NOMAD_*`
environment variables remain compatibility inputs. Prefer `WANDER_*` aliases
where Wander provides them for new automation.

For a local, non-production smoke test:

```shell
wander agent -dev
```

The API listens on the configured HTTP address. The embedded UI is available
at `/ui/`, and `/` redirects there. It is enabled by default and can be disabled
without disabling the API:

```hcl
ui {
  enabled = false
}
```

Production agents should continue to use explicit server/client configuration,
persistent `data_dir` storage, TLS, ACLs, and the same service supervision used
for the 1.6.5 deployment. Change the service executable from `nomad` to
`wander`; do not rename or recreate the existing data directory during a
rolling migration.

## Migrate from Nomad 1.6.5

The tested migration is a rolling binary replacement that preserves the
existing state and configuration.

1. Confirm every server and client reports open-source Nomad 1.6.5.
2. Confirm the cluster has a healthy leader and quorum, and that expected
   clients and workloads are healthy.
3. Save a snapshot and copy it off the cluster:

   ```shell
   nomad operator snapshot save pre-wander.snap
   ```

4. Retain the exact Nomad 1.6.5 executable and service definition for rollback.
5. Replace one server executable with Wander, restart that server, and wait for
   it to rejoin before continuing. Never restart multiple voting servers at the
   same time.
6. After each server replacement, verify leader/quorum health, variables, jobs,
   allocations, and ACL access.
7. When all servers run Wander, replace clients in controlled batches. Drain a
   client first when workload policy requires rescheduling rather than an
   in-place client restart.
8. Verify the UI, logs, exec, job mutations, namespaces, regions, services, and
   a representative workload before declaring the migration complete.

Do not run Nomad and Wander concurrently against the same local data directory.

## Upgrade within Wander 0.1.x

Use the same rolling procedure for a 0.1.x patch upgrade:

1. Read the changelog and known limitations.
2. Verify the archive checksum and retain the installed binary.
3. Save and verify a fresh snapshot.
4. Upgrade servers one at a time, waiting for membership and quorum health.
5. Upgrade clients in controlled batches.
6. Exercise representative API, UI, scheduling, log, and exec operations.

Do not skip directly across a release whose notes require an intermediate step.

## Roll back

If a binary replacement fails before incompatible state has been written:

1. Stop the affected Wander agent.
2. Restore the retained Nomad 1.6.5 or previous Wander executable.
3. Start the agent with the unchanged configuration and data directory.
4. Wait for it to rejoin and verify cluster health before rolling back another
   node.

The release gate rehearses rollback to Nomad 1.6.5 after a Wander rolling
upgrade. A snapshot restore is a disaster-recovery action, not the first
rollback step.

## Back up and restore

Create an atomic Raft snapshot from the leader:

```shell
wander operator snapshot save backup.snap
```

Use `-stale` only during a leader outage when a potentially stale snapshot is
better than no snapshot. Record the Wander version, configuration, TLS files,
encryption key material, plugins, and external Consul/Vault data separately;
they are not all contained in the Raft snapshot.

Test snapshots by restoring them into an isolated recovery cluster. Restore is
a low-level operation intended for disaster recovery and should target a fresh
cluster with no concurrent workload changes:

```shell
wander operator snapshot restore backup.snap
```

After restore, verify leader/quorum health, ACL access, namespaces, variables,
jobs, evaluations, deployments, and client re-registration before accepting
traffic.

## Known limitations for 0.1.0

- Only open-source Nomad 1.6.5 is a supported Nomad migration source.
- Preview builds are not the stable drop-in release.
- GitHub release archives are the authoritative install source until
  Wander-owned package repositories are published.
- Dark/system theme support is deferred; the 0.1.0 UI ships in light mode.
- OpenBao support is planned after 0.1.0; the current secrets integration keeps
  the inherited Vault-compatible behavior.
- Existing compatibility identifiers such as `/v1/`, `X-Nomad-Token`,
  `.nomad` job files, and inherited `NOMAD_*` variables remain intentional.

## Troubleshooting

Start with the agent logs and these checks:

```shell
wander version
wander server members
wander node status
wander status
curl --fail --silent http://127.0.0.1:4646/v1/agent/self
```

- If the UI is unavailable, confirm the API responds, the `ui` stanza is not
  disabled, and browse to `/ui/`. The UI is served by the Wander binary.
- If the UI says disconnected, check browser network requests, TLS trust,
  reverse-proxy forwarding, ACL token validity, and API reachability.
- If a server does not rejoin during a rolling operation, stop and restore
  quorum before changing another server.
- If jobs cannot be read or changed, verify the selected namespace/region and
  the token's ACL capabilities.
- If logs or exec fail while other pages work, verify client reachability and
  reverse-proxy support for streaming responses and WebSocket upgrades.
- If a migration result differs from Nomad 1.6.5, stop the rollout, retain
  diagnostics with `wander operator debug`, and roll back the affected node.

Do not include ACL tokens, private keys, secrets, or unredacted debug archives
in public GitHub issues.
