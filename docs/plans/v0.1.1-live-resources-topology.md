# Wander 0.1.1 Live Resources and Topology

## Context

Post-release review of the 0.1.0 binary found two operational UI gaps: allocation
resource samples remain fixed until the browser is refreshed, and the topology
page exposes relationships as cards without an immediately readable view of
each allocation's reservation against total node capacity.

## Research Findings

- Allocation detail already reads aggregate and per-task client statistics,
  but only while initially rendering the Tasks tab.
- Existing deployment, evaluation, and job-allocation views use bounded HTMX
  polling. Allocation statistics can follow that established pattern without
  a new JavaScript dependency.
- The current topology projection already has node capacity and per-allocation
  CPU and memory reservations, as well as filters and scoped links. The missing
  piece is presentation rather than another API read.
- Topology data represents scheduler reservations, not live host utilization;
  the new capacity map must retain that distinction.

## Acceptance Criteria

- [x] Running allocation resource statistics refresh without a full page load.
- [x] Polling preserves namespace, region, and ACL context and stops for a
      terminal allocation.
- [x] A failed statistics refresh renders a truthful unavailable state without
      hiding the rest of the allocation page.
- [x] Aggregate and per-task CPU/memory samples update together.
- [x] Every topology node shows allocation reservations against full CPU and
      memory capacity, controlled by the existing Metrics filter.
- [x] Allocation segments remain accessible, linked, and clearly labelled as
      reservations rather than utilization.
- [x] Focused handler/template tests and the embedded release browser suite
      cover both behaviors.

## Technical Approach

1. Add a scoped allocation-statistics partial endpoint that fetches only the
   allocation record and client statistics needed for the live panel.
2. Extract aggregate and per-task live-resource markup into one polling
   component and keep reserved-resource data in the static task cards.
3. Poll the component every three seconds only while the allocation is
   running, replacing only that component so tab, focus, and scroll state are
   preserved.
4. Render CPU and memory capacity tracks from existing topology data. Size each
   allocation segment relative to the node total and retain a visible free
   capacity remainder.
5. Add deterministic handler/template assertions and live-browser assertions,
   then update the release checklist and changelog.

## Testing Strategy

- Go handler tests for scoped statistics polling, changing samples, terminal
  behavior, and unavailable statistics.
- Template/handler tests for topology tracks, segment labels, links, and
  metric-filter behavior.
- Existing complete UI Go suite and embedded Chromium release suite.
- Formatting, generated-template checks, static analysis, vulnerability and
  license gates as required by the release workflow.

## Risks and Mitigations

- Frequent full allocation rendering would repeat unrelated service/history
  reads. Use a dedicated statistics endpoint and replace only the live panel.
- Polling can disrupt operator interaction. Keep it isolated from tabs,
  controls, and scroll containers.
- Oversubscribed resources can exceed node capacity. Clamp visual segment
  widths while continuing to display the exact reservation values in labels.
- A capacity chart could be mistaken for load. Use “reserved” and “capacity”
  throughout and never call these values utilization.
